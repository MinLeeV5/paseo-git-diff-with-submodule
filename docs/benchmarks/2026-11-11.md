# GitLens v0.6.0 与 Paseo v0.16.0-beta.1 性能对测

主测试完成时间：2026-11-11T14:16:59.890Z。主测试与独立复测均使用真实的本地 daemon、WebSocket 和固定版本源码。

GitLens 的按文件加载适合快速打开选中文件；Paseo 的批量读取与紧凑传输在全量数据读取上有可借鉴之处。10 仓库样本中，GitLens 的整份快照扫描明显增加文件打开等待。具体结果如下。

## 环境与方法

- 机器：Apple M5，10 个逻辑 CPU，24 GiB 内存；darwin 25.6.0 arm64。
- Node v24.22.2；git version 2.52.0。
- GitLens v0.6.0，固定提交 `c39dcdfc80994b9672701059c1e5878ddf2f67a3`，通过 `git archive` 提取独立源码，加载到测试 daemon。
- 官方 npm `@getpaseo/server`、`client`、`protocol`、`plugin`、`highlight`、`cli` 均为 0.16.0-beta.1；所用包的完整性标识保存在原始数据中。
- 两边使用同一个隔离 daemon、同一个 SDK 和真实 loopback WebSocket；未升级或连接日常使用的 daemon。未预注册工作区，也未注入后台 Git 压力；原生 Git 保持默认 8 并发、64 次启动/秒，插件保持默认 6 并发。
- 隔离的是 daemon 配置、源码和比较缓存；CPU、磁盘仍与本机其他工作共享，没有做系统级资源隔离。负载异常与独立复测记录见文末。
- 每场景先排除 1 轮预热，再测 7 轮。每轮复制相同仓库到新路径，以清空比较键与插件快照缓存；OS 文件缓存保持热态。daemon 启动、建库、复制、预热和间隔等待均不计时。
- 三种模式轮换顺序，串行执行；每种模式开始前等待 1100 ms，避免上一模式消耗的 Git 启动限流窗口影响下一模式。
- 报告使用中位数；括号为 7 次样本的最小值–最大值。没有据此估计长期 P95 或 FPS。每个样本保存了宿主负载。

## 快照过期与子模块

下表只测 GitLens：服务端补丁已命中缓存，等待 1100 ms 让快照过期，再发起同一文件 RPC。等待本身不计时。返回前重新扫描整个工作区的时间仍包含在 RPC 中。这不代表前端已保留标签切换时的耗时：前端标签缓存命中可以完全不发 RPC。

| 场景                          | 热缓存文件 RPC / ms | 快照过期后，同一缓存文件 RPC / ms |
| ----------------------------- | ------------------- | --------------------------------- |
| 50 个已跟踪文件               | 0.3（0.2–1.3）      | 173.4（111.9–471.6）              |
| 500 个已跟踪文件              | 0.2（0.2–0.3）      | 245.3（210.4–453.5）              |
| 1000 个已跟踪文件             | 0.2（0.2–0.3）      | 336.2（270.2–586.1）              |
| 500 个修改 + 500 个未跟踪文件 | 0.2（0.1–0.3）      | 248.3（196.9–299.8）              |
| 12000 行单文件，400 处修改    | 5.6（4.9–7.8）      | 172.0（136.4–218.1）              |
| 10 个仓库，共 200 个文件      | 0.3（0.2–0.7）      | 1970.0（1813.0–2152.8）           |

子模块样本为主仓 + 8 个子模块 + 1 个嵌套子模块，每仓 20 个已跟踪文件发生修改，均配置 `ignore=all`。GitLens 返回 10 个仓库、200 个文件，文件列表中位数为 2073.3 ms，首个文件为 2099.5 ms。Paseo 原生根仓比较返回 20 个文件，首个 ready 为 549.6 ms。两者覆盖范围不同，此处不计算速度倍数。

原始数据也包含 Paseo 在已有订阅保留时，第二订阅重放整个比较的缓存耗时 `cacheMs`；其工作量是全量比较，GitLens 的 `cacheMs` 是单文件，两者不作为等量缓存对比。

## 校验与结论边界

共计 126 个正式样本，另有 18 个不进入统计的预热样本。相同工作量的五个场景均校验文件清单、增删行数，以及所有新增/删除行的路径、类型、文本 SHA-256，一致后才计入结果。未接受二进制、超限或省略占位。

这组结果支持优先拆分主仓和子模块快照、减少打开文件对整份扫描的依赖，并继续保留按需加载。批量 Git 补丁获取和紧凑传输值得在需要多文件数据时借鉴。刷新不闪烁属于 UI 行为，本轮没有验证；繁忙 daemon 的调度优先级、网络 RTT、真实移动设备和浏览器 FPS 也没有覆盖。

## 复现

macOS arm64 下，在仓库目录执行（依赖安装不计时）：

```bash
npm ci
mkdir -p artifacts/benchmark-comparison/runtime
npm install --prefix artifacts/benchmark-comparison/runtime --no-audit --no-fund --ignore-scripts --omit=optional --legacy-peer-deps --save-exact @getpaseo/server@0.16.0-beta.1 @getpaseo/client@0.16.0-beta.1 @getpaseo/cli@0.16.0-beta.1 @esbuild/darwin-arm64@0.25.12
node_modules/.bin/tsx scripts/benchmark-upstream.ts
```

可用环境变量：`PASEO_BENCH_ROUNDS`（默认 7）、`PASEO_BENCH_CASES`（逗号分隔的场景名）、`PASEO_BENCH_GITLENS_REF`（默认 v0.6.0）、`PASEO_BENCH_RUNTIME`、`PASEO_BENCH_OUTPUT`。脚本只启动和关闭自己的临时 daemon，结束后清理临时仓库和 daemon home。

仓库内保存的 [完整原始数据](2026-11-11.json) 与 [对测脚本](../../scripts/benchmark-upstream.ts) 可用于复核；本地完整控制台输出和 daemon 日志在 `artifacts/benchmark-comparison/`。
